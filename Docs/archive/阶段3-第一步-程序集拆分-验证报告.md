# 阶段 3 第一步验证报告：`Utils` 能不能拆成两个程序集

> **已归档（2026-10-25）**：本文是阶段 2 / 阶段 3 时期的历史记录，相关改造已完成，不再维护；其中的路径与命令可能已过时，以当前代码为准。

> 对应 [阶段3-执行清单](阶段3-执行清单.md) 的第 1 步「先动程序集，不动命名空间」。
> 结论：**能拆，且一条 `.cs` 都不用改**。下面是证据。

## 要证明什么

执行清单里第 1 步的说法是：

> 这一步 `.cs` 文件一个字节都不改，只有 `.asmdef` 变化。

这个说法如果错了，代价很大：拆完程序集发现两个半区互相引用，就要么回滚，要么临时加互相引用（形成环），
把最简单的步骤变成最脏的一步。

所以先证明三件事：

1. `Utils/Util` + `Utils/UI` 这 72 个文件，**不依赖**其余 101 个文件
2. 其余 101 个文件，**可以**单向依赖那 72 个
3. 两半各自都能编译通过

## 方法

不猜、不靠读代码：直接拿 Unity 生成的真实编译清单做实验。

```
Astray.Utils.csproj
├── 173 个 <Compile Include="Assets\...">      ← 真实参与编译的文件清单
├── 299 个 <Reference> / <ProjectReference>    ← 真实引用集
└── DefineConstants / TargetFramework 等       ← 真实编译条件
```

按目录前缀切成两份，各自生成一个 csproj，然后用 `dotnet build` 分别编译：

| 产物 | 内容 | 额外引用 |
|---|---|---|
| `Astray.Utilities` | `Utils\Util\**` + `Utils\UI\**`（72 个文件） | 无 |
| `Astray.Framework.Modules` | 其余 101 个文件 | **引用 Utilities** |

如果 Utilities 单独编译失败 → 它依赖 Modules，边界不对；
如果 Modules 引用 Utilities 后编译失败 → 还有反向依赖，边界也不对。

## 结果

| 构建 | 结果 |
|---|---|
| `Astray.Utilities`（无任何对外引用） | **0 错误** |
| `Astray.Framework.Modules`（引用 Utilities） | **0 错误 0 警告** |

说明：

- 那 72 个文件（`AlgorithmUtil`、`StringUtil`、`LoopScrollRect`、`ImageEx`、`TreeView`…）**没有一行用到**
  Network / Http / Timer / ObjectPool 里的东西；
- 反向是有依赖的（`Utils/Network` 用到 `StringUtil`、`Utils/Http` 用到 `AlgorithmUtil` 之类），
  方向是 **Modules → Utilities**，正好是分层要的方向；
- 两半都引用了 `Base` / `Common` / `UniTask`，这个共享没问题。

## 这意味着什么

1. **零代码改动**：不需要改任何 `namespace`、任何 `using`、任何类型名。执行清单第 1 步的说法成立。
2. **零资产风险**：文件不移动，`.meta` 和 GUID 都不动，Addressables 地址和 prefab 引用完全不受影响。
   这一步是整个阶段 3 里唯一"动程序集又不动资产"的窗口。
3. **顺序确定了**：必须先建 `Utilities`，再让 `Modules` 引用它；反过来会成环。

## 剩下的手工步骤（只能在 Unity 里做）

编译层面已经证明可行，但 asmdef 本身还得改。需要更新的引用方一共 **10 个**：

| asmdef | 拆分后应引用 |
|---|---|
| `Core\Astray.Core.asmdef` | Modules + Utilities |
| `Core\System\UISystem\Editor\Astray.Core.Editor.asmdef` | Modules + Utilities |
| `Tests\Astray.Tests.asmdef` | Modules + Utilities |
| `Utils\ColliderUtil\Editor\...ColliderUtil.Editor.asmdef` | 视用到的类型选 |
| `Utils\CSG\Example\Scripts\Editor\...CSG.Example.Editor.asmdef` | 视用到的类型选 |
| `Utils\Deadline\Editor\...Deadline.Editor.asmdef` | Modules |
| `Utils\Network\Editor\...Network.Editor.asmdef` | Modules |
| `Utils\UI\ButtonExtensions\Animated\Editor\...asmdef` | Utilities |
| `Utils\UI\ButtonExtensions\Click\Editor\...asmdef` | Utilities |
| `Utils\UI\ImageExtensions\Editor\...asmdef` | Utilities |

前 3 个是两个都要；后面 7 个按"它引用的类型属于哪一半"选一个。
选错了 Unity 会立刻报 `CS0246`，比运行时才发现好得多。

另外还有一件容易被忘的事：**守卫的依赖方向表要同步加新名字**。

```csharp
// Editor/Toolbox/Guards/ArchitectureGuard.cs 的 ForbiddenReferences
["Astray.Framework.Modules"] = new[] { "Astray.Core", "Astray.Core.Editor" },
["Astray.Utilities"]         = new[] { "Astray.Core", "Astray.Core.Editor" },
```

不加的话，拆分之后"下层不许引用上层"这条规则对新增的两个程序集就失效了。

## 这个证明**没有**覆盖什么

诚实列清楚，免得被当成"阶段 3 已经做完"：

| 没覆盖 | 原因 |
|---|---|
| asmdef 的 GUID 与引用关系 | 模拟用的是 csproj，不是 asmdef；Unity 侧的引用要手工加 |
| 编译顺序 / 循环引用检测 | Unity 自己会算；这里只证明没有环的**需求** |
| 运行时行为 | 拆程序集不改变任何类型，理论上无行为变化，但仍需跑一次全部测试 |
| 编辑器脚本（`*/Editor/*.asmdef`） | 它们有独立 asmdef，没参与这次模拟 |
| 命名空间 | 本次刻意不动命名空间，所以 `Astray.Common.Util` 一半在 Utilities、一半在 Modules——**看起来很怪，这是预期的中间状态** |

## 复现

```powershell
# 1. 先让 Unity 生成 csproj（或已有）
cd Unity/Astray
dotnet build Astray.Utils.csproj -v q --nologo

# 2. 跑模拟：切分 → 生成两个 csproj → 分别编译
cd ..\..\
powershell -NoProfile -ExecutionPolicy Bypass -File Tools\phase3-split-sim.ps1   # 该一次性脚本已随本次整理删除
```

输出最后两行就是结论：

```
=== PASS: the folder boundary is a valid assembly boundary ===
    Utilities  = 72 files, no outward dependency
    Modules    = 101 files, depends on Utilities (one way)
```

产物落在 `Unity/Astray/Temp/phase3sim/`（已被 gitignore），随时可以删。

## 补充：改名的真实影响面（同样实测）

"把 `Core` 改名为 `Framework.Runtime`"听起来吓人，实际影响面可以穷举。搜了一遍
**代码里的字面量**（不是命名空间，命名空间这次不动）：

| 字面量 | 出现次数 | 位置 |
|---|---|---|
| `"Astray.Core"` | 5 | `Core/Base/AssemblyInfo.cs` 1 处 + 守卫的同名表 4 处 |
| `"Astray.Utils"` | 4 | `Core/Base/AssemblyInfo.cs` 1 处 + 守卫 3 处 |

**没有任何** `Type.GetType("..., Astray.Core")`、`Assembly.Load("Astray.Core")`、
或反射拼程序集名的写法。也就是说没有"运行时才炸"的隐式依赖，改名失败一定在编译期暴露。

所以一次改名要动的东西是：

1. `Astray.Core.asmdef` / `Astray.Utils.asmdef` 的 `name` 字段（**文件名和 GUID 可以不动**）
2. 引用它们的那 10 个 asmdef 里的字符串
3. `Core/Base/AssemblyInfo.cs` 的 `InternalsVisibleTo`（改完还要补上新拆出来的两个名字）
4. `ArchitectureGuard.cs` 的 `ForbiddenReferences` 表

一共 4 类、十几行文本，全部是编译期可见的——这是"这步风险可控"的直接依据。

> 顺带一个设计上的好消息：`InternalsVisibleTo` 只有 2 条，说明跨程序集的 internal 依赖很浅。
> 等阶段 2 遗留的三个 MonoBehaviour 模块改成纯 C# 之后，这两条也能一并删掉（见
> [阶段2-遗留-MonoBehaviour模块改造方案](阶段2-遗留-MonoBehaviour模块改造方案.md) 第六节）。
