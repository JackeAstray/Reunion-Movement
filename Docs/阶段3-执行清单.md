# 阶段 3 执行清单：分层与命名归位

> 阶段 3 是整套重构里**唯一动路径**的阶段，也是唯一必须在 Unity 编辑器里做完才敢提交的阶段。
> 本文把它拆成可勾选的步骤，保证每一步都能独立回滚，且任何一步失败都不会留下半迁移状态。
>
> 相关背景见 [重构方案](重构方案.md) 第 313 行「阶段 3」。

## 为什么必须等编辑器

| 风险 | 只改磁盘会发生什么 | 编辑器里做为什么安全 |
|---|---|---|
| 移动 `.cs` 不带 `.meta` | GUID 重新生成，所有 prefab / scene 里的组件引用变成 `Missing` | 拖拽 = 移动 `.meta`，GUID 不变 |
| 改程序集名 | 用**名字**引用它的 asmdef 全部断裂（本仓库 26 个 asmdef 里只有 1 处用 GUID 引用，其余全按名字） | 改名后 Unity 会提示修复，且能立刻看到报错 |
| 改命名空间 | 部分 Addressables 地址由类型全名生成，地址会失效 | 改完能立刻跑「Addressables → 校验地址」 |

命名空间与目录已经**对不上**，这是新人绕路的直接原因之一：

| 文件所在目录 | 实际命名空间 | 问题 |
|---|---|---|
| `Utils/Util/` | `ReunionMovement.Common.Util` | 目录叫 Utils、命名空间叫 Common |
| `Utils/UI/ImageExtensions/` | `ReunionMovement.UI.ImageExtensions` | 跳过了 `Utils` 层级 |
| `Utils/Network/` | `ReunionMovement.Common.Util.Network`（部分） | 三层前缀，与目录无关 |
| `Core/Base/` | `ReunionMovement.Core.Base` | 目录层级与命名空间一致，但程序集叫 `Base` |

## 目标结构

```
Assets/ReunionMovement/
├── Base/            → ReunionMovement.Base                    （不动）
├── Common/          → ReunionMovement.Common                  （不动）
├── Framework/
│   ├── Modules/     → ReunionMovement.Framework.Modules       ← 原 Utils 里的"可复用模块"
│   └── Runtime/     → ReunionMovement.Framework.Runtime       ← 原 Core/
└── Utilities/       → ReunionMovement.Utilities               ← 原 Utils/Util + Utils/UI
```

模块与工具的划分标准：**"它自己会跑吗？"**

- 有生命周期、需要被 `GameEngine` 驱动或有状态的 → `Framework/Modules`（Network/Http/Download/Timer/StateMachine/ObjectPool/GachaSystem/ScreenLogger/…）
- 纯函数、无状态、给谁都能用 → `Utilities`（AlgorithmUtil/StringUtil/ImageExtensions/LoopScrollRect/…）

## 执行顺序（严格按序，每步一个提交）

### 第 1 步：先动程序集，不动命名空间

```powershell
# 目标：Utils 拆成两个 asmdef；Core 改名为 Framework.Runtime
# 关键：这一步 .cs 文件一个字节都不改，只有 .asmdef 变化
```

1. 在 `Utils/` 下新建两个 asmdef：`ReunionMovement.Framework.Modules.asmdef`、`ReunionMovement.Utilities.asmdef`，
   分别把对应子目录的文件纳入（Unity 里选中目录 → `Assets/Create/Assembly Definition`，再在 Inspector 里填 `rootNamespace`）。
2. 删除原 `ReunionMovement.Utils.asmdef`（Unity 会重新分配 GUID）。
3. 把所有引用 `ReunionMovement.Utils` 的 asmdef 改成引用新的两个。
4. **验证**：Unity 编译 0 error → `dotnet build` 19 个程序集 0 error → 跑一次 Play。

这一步之后命名空间仍然全乱，但**程序集边界已经正确**，后续改名才有落脚点。

### 第 2 步：再动命名空间（不做这一步就不要做第 3 步）

```text
Rider / VS：右键命名空间 → Rename → 填映射表里的新名字 → 勾选"包括注释和字符串"
```

- 一次只改一个命名空间，改完立刻编译 + 跑测试；
- 改完立刻 `git commit`，别攒着；
- **不要**用正则批量替换 `.cs` 里的 `using`——`ReunionMovement.Core` 既出现在 `using` 里也出现在 `typeof(...)` 字符串里，正则一定会误伤。

### 第 3 步：最后动目录

```powershell
# 每个目录一次，.cs 与 .meta 必须同进同出
git mv Unity/ReunionMovement/Assets/ReunionMovement/Utils/Util `
       Unity/ReunionMovement/Assets/ReunionMovement/Utilities
git mv Unity/ReunionMovement/Assets/ReunionMovement/Utils/Util.meta `
       Unity/ReunionMovement/Assets/ReunionMovement/Utilities.meta
```

**校验脚本**：移动后立刻跑守卫的 `.meta` 检查，任何漏掉的 `.meta` 都会被抓出来：

```bash
Unity -batchmode -quit -projectPath Unity/ReunionMovement \
      -executeMethod ReunionMovement.Editor.Guards.ArchitectureGuard.RunAllBatch
```

`.meta` 检查通过 + 编译 0 错误，才可以继续下一个目录。

## 验收清单

| # | 检查项 | 通过标准 |
|---|---|---|
| 1 | 程序集依赖方向 | 守卫 `AssemblyReferences_PointDownwards` 绿 |
| 2 | 缺失 `.meta` | 守卫 `EverySourceFile_HasMeta` 绿 |
| 3 | 编译 | `dotnet build` 19 个程序集 0 error；Unity Console 0 error |
| 4 | 单元测试 | Test Runner EditMode 全绿（101 个用例） |
| 5 | 示例场景 | `Scenes/StartGame.unity` + 至少 3 个示例场景 Play 无 `Missing` |
| 6 | Addressables | 菜单「Addressables → 校验地址」无缺失 key |
| 7 | 预制体引用 | 全局搜 `Missing (Mono Script)` 为 0 |

第 5–7 项是阶段 3 的**真正验收标准**，编译通过只说明代码没散架。

## 回滚

每个步骤一个独立提交，出问题 `git revert <commit>` 即可回到上一步——
前提是**三步严格分开提交**，不要一次性把所有改名塞进一个 commit。

## 已知的坑

| 坑 | 说明 |
|---|---|
| `ReunionMovement.Core` 出现在字符串里 | `Addressables` 地址、`Reflection` 查找、`SerializedProperty` 路径里都有，改名时搜一遍 |
| Editor 专用程序集 | `ReunionMovement.Core.Editor` 跟随 `Framework.Runtime`，但 `Editor/` 下还有 `ReunionMovement.EditorTools`、`Toolbox.Editor` 不跟着改 |
| 示例程序集 | `ReunionMovement.Example`（10 个文件）依赖 Core，改名后要一起改引用 |
| 第三方 | `Plugins/`、`3rd/` 下的 asmdef 一律不动 |
