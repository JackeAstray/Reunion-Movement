# 05 · 常见陷阱

这些坑的共同点：**编译通过、运行不报错，但行为不对**。按踩到的频率排序。

## 1. 双重驱动（已消除，保留为历史教训）

驱动链只有一条：

```
GameEngineDriver (MonoBehaviour)  →  GameEngine.OnUpdate  →  各模块的 Update(logicTime, realTime)
```

历史上 `TimerMgr` / `HttpMgr` / `NetworkMgr` 同时也是 `MonoBehaviour` 单例，自己还有一个 `Update`，
用 `ModuleRuntime.IsEngineRunning` 判断是否兜底。现在：

- `TimerMgr` / `HttpMgr` / `NetworkMgr` 都已改为纯 C# 单例，只由引擎驱动；
- 两个旧示例场景里的 `NetworkMgr` 组件已换成空的 `NetworkMgrSceneAdapter`，避免 Missing Script，可删除；
- 无引擎时显式调用对应模块的 `Tick()`（Timer/Http/Network 都有）；
- `ModuleRuntime` 已删除，不再有 `IsEngineRunning` 兜底开关。

**新增模块只实现 `ISystemUpdatable`**，让引擎驱动；不要为了“脱离引擎也能跑”再加一套本地 Update。

## 2. 暂停：别自己写 `Time.timeScale = 0`

`PauseSystem` 用**多原因计票**：多个系统各自 `RequestPause(reason)`，全部 `ReleasePause` 后才真正恢复。
一方误释放不会打断其他系统的暂停。

```csharp
PauseSystem.Instance.RequestPause(this);   // 我需要的暂停
PauseSystem.Instance.ReleasePause(this);   // 我不要了
```

几个容易忽略的点：

| 现象 | 原因 |
|---|---|
| 暂停期间 UI 动画停了、网络心跳也停了 | `timeScale = 0` 让 `logicTime` 归零。暂停期仍需工作的逻辑要用 `realTime` 参数 |
| 从慢动作恢复后 `timeScale` 变成 1，慢动作没了 | 系统会还原**进入暂停前**的 `timeScale`，如果你在暂停期间改 `timeScale` 会被覆盖 |
| 切后台回来，游戏卡在暂停 | `AudioListener.pause` 与游戏级暂停是两套状态，`Clear()` 里必须都还原 |

暂停期间模块的 `Update` **仍然会被调用**，这是刻意的：`timeScale = 0` 已经把 `logicTime` 归零，
模块可以自己决定用 `realTime` 做什么。

## 3. Addressables 双轨：异步优先，同步只能走 Resources

```
异步开窗（OpenWindowAsync&lt;TWindow, TArgs&gt;） → Addressables（AddressableKeys.UIRoot + name）
                 ↘  失败  →  Resources（Config.UIPath + name）
同步加载（内部 LoadWindow，已 internal） →  Resources only
```

同步路径**永远只走 Resources**，因为 Addressables 没有真正的同步加载，WebGL 更不支持 `WaitForCompletion`。

所以：在 `Resources/` 下找不到同名 prefab，同步加载就是 null，而异步加载还能从 Addressables 拿到。

## 4. WebGL 的四个差异

| 差异 | 影响 |
|---|---|
| `PlayerPrefs` 落盘 → IndexedDB | 启动时会阻塞等载入；别在 `Awake` 里假设存档已就绪 |
| 不支持线程 | 任何 `Thread` / `Task.Run` 都会抛异常，用 `UniTask` 或协程 |
| 全屏必须走 JS 桥接 | 见 `StartGame.cs` 里 `#if UNITY_WEBGL && !UNITY_EDITOR` 的 `DllImport("__Internal")` 段；编辑器里**永远编译不到**这些分支，改动只能靠真机构建验证 |
| 没有真正的"退出" | `Application.Quit()` 在 WebGL 上不生效，需要显式处理（本项目 `AlgorithmUtil.Quit()` 已做平台守卫） |

## 5. 关闭 Domain Reload 后，静态单例把上一局的对象带进来

Unity 6 可以在 `Project Settings → Editor → Enter Play Mode Options` 里关掉 Domain Reload 来加速迭代。
关掉之后，`SingletonMgr<T>.instance` 这类静态字段**不会自动清空**，会指向上一会话已销毁的对象。

项目的对策是 `SubsystemRegistration` 阶段的静态复位：`Bootstrap.ResetStaticStateOnPlay()` 复位引擎与入口缓存，
Modules 程序集的 `SingletonResets.ResetAll()` 复位 7 个 MonoBehaviour 单例（Runtime 不引用 Modules，由 Modules 自己注册）：

```csharp
// Framework/Runtime/StartGame 之外的任意新增 SingletonMgr<T> 子类，都要在这里补一行
HttpMgr.ResetStatics();
NetworkMgr.ResetStatics();
TimerMgr.ResetStatics();
// …
```

漏掉的症状是"第一次 Play 正常，第二次 Play 报 `MissingReferenceException`"。

## 6. `.Instance` 和 `Modules.Get<T>()` 混用

| 场景 | 用哪个 | 原因 |
|---|---|---|
| 运行中的游戏逻辑 | `Modules.Get<T>()` | 引擎已启动，取不到会抛异常并列出已注册模块 |
| 编辑器工具 | `Xxx.Instance` | 编辑器里没有引擎实例 |
| 单元测试 | `Xxx.Instance` | 测试不启动引擎，跑得更快 |
| 模块内部互调 | 直接字段 | 同程序集内没必要再查表 |

守卫会拦住**新增**的 `.Instance` 调用点（基线见 `instance-usage-baseline.txt`），
所以运行时新写的代码请直接用 `Modules.Get<T>()`。

## 7. 模块顺序出错时的排查顺序

启动日志里有一行：

```
模块顺序: ResourcesSystem(10) → AddressableSystem(20) → … → HttpMgr(140)
```

如果这行变成告警 `模块顺序构建失败: …`，说明 `ModuleCatalog` 校验没通过，四类原因：

| 报错 | 原因 | 修法 |
|---|---|---|
| 重复注册 | 同一个实例 `Add` 了两次 | 删掉多余的 |
| 缺少依赖 | `[ModuleOrder(_, typeof(X))]` 里的 X 没注册 | 把 X 加进 `CreateModules()`，或去掉这个依赖 |
| 自己依赖自己 | 参数写错 | 改 `[ModuleOrder]` |
| 成环 | A 依赖 B，B 又依赖 A | 拆依赖：用事件/接口代替直接依赖 |

校验失败时引擎**不会中止启动**，而是退回声明顺序继续跑——所以它只会告警，不会崩。
看到告警就要处理，别当没看见。

## 8. 写 EditMode 测试时会踩的两个坑

```csharp
[SetUp]
public void SetUp()
{
    originalTimeScale = Time.timeScale;   // ① 全局状态要存旧值
    Time.timeScale = 1f;
    PauseSystem.Instance.Clear();         // ② 单例跨用例残留状态
    PauseSystem.Instance.Init();
}

[TearDown]
public void TearDown()
{
    PauseSystem.Instance.Clear();
    Time.timeScale = originalTimeScale;   // ① 必须还原，否则影响后面所有用例
}
```

- **①** `Time.timeScale`、`AudioListener.pause`、`Cursor.visible` 都是全局的，改了就污染后续用例；
- **②** 单例是 `Lazy<T>` 静态的，上一个用例的暂停原因会留到下一个用例，必须 `Clear()` 复位。

另外：测试里把 `pauseAudioOnPause = false` 关掉，可以避免依赖 `GameOption` 的全局配置，
让测试只测暂停逻辑本身。

## 9. 面板里别写 `async void OnOpen`

`async void` 的异常在第一个 `await` 之后就没人接住了——Unity 只会记一条未处理异常，调用方拿不到失败。

UI Toolkit 面板把异步逻辑放基类提供的 `OnOpenAsync`，异常由基类统一记录：

```csharp
// ✅ 基类接住异常，子类不用写 try/catch
protected override async UniTask OnOpenAsync(object data)
{
    await base.OnOpenAsync(data);
    await PlayAnimation();
}

// ❌ 不要这样写
public override async void OnOpen(object data = null) { ... }
```

`OnOpen(object)` 仍是同步入口（置 `IsOpen`、显示根元素、再启动 `OnOpenAsync`），所以打开流程不用改。
uGUI 那边 `UIController.OnOpen()` 本身是同步的；确实需要异步时用 `FadeIn/FadeOut`，
或在方法内 `SomeAsync().Forget(ex => Log.Error(...))`。
