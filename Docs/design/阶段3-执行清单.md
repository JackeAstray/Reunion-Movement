## 二、与原计划的偏差（重要）

**原计划第 1 步"先建两个 asmdef、不动目录"不可行**：asmdef 的作用域是"它所在目录及其全部子目录"，而 `Utils/Util` 与 `Utils/UI` 是**兄弟目录**，一个 asmdef 盖不住两者。要么先移动到一个共同父目录，要么拆成 3 个程序集。

因此正确顺序是：**移动目录 → 建 asmdef → 改命名空间**（原计划把移动放在第 3 步）。

## 三、已完成的可行性验证

按目标划分（`Util` + `UI` → Utilities，其余 → Framework.Modules）用 Unity 自己的 rsp 参数做了两次独立编译：

```
Utilities（76 文件，排除各目录下 Editor/）        → 0 error
Framework.Modules（101 文件，引用 Utilities）      → 0 error
```

结论：**两个方向没有循环依赖**，拆分在编译层面可行。（`Base` 里的 `InternalsVisibleTo("Astray.Utils")` 只授予 setter，拆分后读侧不需要它。）

## 四、路径耦合清单（实测，移动前必须逐条处理）

先说结论：**编辑器工具已经全部通过 `AstrayPaths` 解析路径**（`CreateUIPlane` 的生成目录、Excel 导表、守卫基线、工具箱、两个打包器都是），
运行时代码也没有硬编码框架路径（只有注释）。所以真正的耦合点只有两处：

| 位置 | 内容 | 处理 |
|---|---|---|
| `Editor/Shared/AstrayPaths.cs` | `CoreAsmdefSuffix = "/Core/Astray.Core.asmdef"`，用它反查框架根 | 移动 `Core/` 后改成新路径；改漏会回退 `FallbackRoot` 并打警告（根目录不变，工具仍能用，只是每次告警） |
| `.github/workflows/unity-ci.yml` | 4 处写死 `$base/Core/...`、`$base/Utils/...` 的 asmdef 依赖方向检查 | 同步路径；注意 `check()` 在文件不存在时 `return 0`，**漏改会静默失效**（规则变成空转） |

不需要改的（已核实）：

- `Tools/upm-publish.ps1`、`AstrayUpmExporter`、`AstrayPackageExporter` 都以框架根为基准，根目录不变；
- `Tests/BootstrapTests.cs` 断言的 `Game/StartGameEntry.cs` 不移动；
- `ArchitectureGuard` / `ToolboxData` 走 `AstrayPaths.InFramework`。

## 五、执行步骤（严格按序，每步一个提交）

### 步骤 1：移动目录（命名空间不动）

```bash
# .cs 与 .meta 必须同进同出；git mv 整目录会一起移动
git mv Unity/Astray/Assets/Astray/Utils/Util \
       Unity/Astray/Assets/Astray/Utilities
git mv Unity/Astray/Assets/Astray/Utils/UI \
       Unity/Astray/Assets/Astray/Utilities/UI
# 其余 Utils/* → Framework/Modules/*
git mv .../Utils/Network .../Framework/Modules/Network
...
```

**验收**：`pwsh Tools/unity-verify.ps1` 全绿（Unity 会重新导入；GUID 随 `.meta` 保留，prefab/scene 引用不受影响）。

> 中间态说明：此时目录已改名、命名空间仍是 `Astray.Common.Util.*`。这是有意的过渡态，只应存在一个提交的时间。

### 步骤 2：建 asmdef

- `Utilities/Astray.Utilities.asmdef`（rootNamespace `Astray.Utilities`）
- `Framework/Modules/Astray.Framework.Modules.asmdef`（rootNamespace `Astray.Framework.Modules`）
- 删除 `Astray.Utils.asmdef`
- 引用方 asmdef 改名（按**名字**引用，共 3 处：`Core`、`Tests`、若干 Editor 程序集）

**验收**：同上；这一步 `.cs` 一个字节不改。

### 步骤 3：改命名空间

按归档清单的映射表逐个改，**一次一个命名空间、改完立刻编译 + 提交**。
不要正则批量替换 `using`（`Astray.Core` 同时出现在 `using` 和字符串里）。

**验收**：`pwsh Tools/unity-verify.ps1` + 菜单「Addressables → 校验地址」无缺失。

执行中的三个实际坑（清单里原先没写）：

1. **`Utils/Util` 与 `Utils/UI` 是兄弟目录**，一个 asmdef 盖不住两者 → 移动与拆程序集必须同一次提交。
2. **同名命名空间跨两个程序集并存**（60 个 Modules 文件与 30 个 Utilities 文件都叫 `Astray.Common.Util`），
   所以命名空间只能**按目录**映射，不能全局替换；而 `using` 两边都要给。
3. **拆分本身会破坏隐式可见性**：以前同处 `Astray.Common.Util` 就能互相看见的类型，现在需要补 `using`；
   `Log` 在 Network 目录与 kcp2k/Telepathy/SimpleWeb 同名 → 需要 `using Log = Astray.Common.Log;` 消歧。
4. **源码生成器是预编译 DLL**（`Plugins/Generators/Astray.SourceGenerator.dll`），
   它用**元数据名字符串**匹配 `[RegisterCommand]` / `UIController`，改命名空间必须同步重建 DLL，
   否则生成物缺失导致编译报错（好在是"响亮"的失败，不是静默失效）。
   重建已脚本化：`pwsh Tools/build-source-generator.ps1`（默认对齐 Unity 6000.3 的 Roslyn 4.3.0）。
