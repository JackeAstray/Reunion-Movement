# Reunion-Movement 重构方案

> 目标：把"新人打开工程 → 跑起来"从 **半天猜** 变成 **10 分钟**，把"加一个系统/窗口"从 **翻 5 个目录** 变成 **改 1 个文件**。
> 现状快照：292 个 C# 文件 / 61,683 行（不含 Plugins、3rd、GenerateScript）。

---

## 一、结论先说

现在的复杂度不是"功能太多"，而是三件事叠在一起：

1. **入口是隐式的，而且写死在框架里。** 没有可点的启动物体，靠 `[RuntimeInitializeOnLoadMethod]` 自动跑；`Bootstrap` 里 `new StartGame()` 写死，`StartGame` 里又写死了 14 个模块、`"Temp"` 场景名、启动窗口。想接入自己的游戏，**必须改框架源码**。
2. **分层是反的。** `Core` 依赖 `Utils`，而 `Utils` 里的东西（网络 / HTTP / 下载 / 计时器 / 状态机 / 对象池）又需要通过"引擎是否在跑"这个全局开关来反向感知引擎 —— 于是有了 `ModuleRuntime.IsEngineRunning` 这种补丁。框架系统被劈成两半，放在两个语义都不对的目录里。
3. **几个巨型类吃掉了全部阅读预算。** `UIInputSystem` 3279 行、`UISystem` 1264 行、`SoundSystem` 1198 行、`GameEngine` 854 行。新人不可能读完，而它们恰好是"必须懂才能改"的部分。

对应地，方案不是"重写"，而是 **先把入口和分层修对（低风险、高收益），再逐个拆巨型类（机械工作、可并行 PR）**。

## 三、九个具体问题（按"上手成本"排序）

### 1. 启动是隐式的，入口不可替换

- `Core/Bootstrap.cs:235` 写死 `var entry = new StartGame();`。想换成自己的入口，只能改这个文件。
- `Core/Bootstrap.cs:99-105` 用**场景名字符串匹配**决定行为：名字以 `Test` / `_` 开头，或包含 `Example` / `UIPlaneScene` / `Music` / `Audio` / `Debug` → 跳过场景跳转。改名即改行为，没有任何界面提示。
- `Core/Bootstrap.cs:69-75` 硬编码 7 个 `XxxMgr.ResetStatics()`。每加一个单例都要回来改这里，否则关掉 Domain Reload 就串场。

> 代价：新人不知道"从哪开始跑"，也不知道"我能不能不用 StartGame"。

### 2. 命名三连撞：`StartGame` 同时是场景、类、UI

- 场景 `Scenes/StartGame.unity`（Build Settings 第 0 个）
- 类 `Core/StartGame.cs`（`GameEntry` 实现）
- 窗口 `StartGameUIPlane`（`UINames.StartGame`）

外加 `Core/StartGame.cs:132` 的魔数 `"Temp"`、`Core/System/SceneSystem/SceneSystem.cs:57` 的魔数 `"LoadingScene"`。四个名字讲同一个"启动"，彼此含义不同。

### 3. 模块顺序靠注释，靠人守

```csharp
// Core/StartGame.cs:55-68
modules.Add(ResourcesSystem.Instance);    // 0: 资源加载（同步/兜底，最高依赖）
modules.Add(AddressableSystem.Instance);  // 1: ……
```

`ICustomSystem` 只有 `Init()`，没有 `Order`、没有 `DependsOn`、没有校验。顺序错了不会报错，只会"某个模块初始化时资源为空"。

### 4. 三套获取对象的方式并存

| 来源 | 写法 | 数量 | 问题 |
|---|---|---|---|
| Core 系统 | `UISystem.Instance`（`Lazy<T>` 自建） | 11 | 引擎没启动也能拿到"看起来可用"的对象 |
| Utils 管理器 | `TimerMgr.Instance`（`MonoBehaviour` 单例） | 8 | 需要 GameObject，生命周期归 Unity |
| 模块列表 | `GameEngine.Current.Modules` | 14 | 几乎没人用，和上面两套重复 |

新人第一个问题必然是"我该用哪个"，而项目里没有答案。

### 5. 两套 Update 驱动

`Utils/Timer/TimerMgr.cs:165`、`Utils/Http/HttpMgr.cs:473`、`Utils/Network/NetworkMgr.cs:271` 都长这样：

```csharp
private void Update()
{
    if (!ModuleRuntime.IsEngineRunning) { TickTimers(Time.deltaTime); } // 引擎没跑，自己驱动
}
```

这确实防住了双重驱动，但代价是：**任何一个系统的执行时机都取决于一个全局布尔值**。调试"为什么这个计时器快了一倍"要同时看引擎和组件。

### 6. 分层反过来，命名空间对不上

- 目录 `Utils/`、程序集 `ReunionMovement.Utils`、rootNamespace **`ReunionMovement.Common.Util`** —— 三处名字都不一样。
- 里面装的是 `Network` / `Http` / `Download` / `Timer` / `StateMachine` / `ObjectPool` / `Gacha`，**这是框架系统，不是工具函数**。
- 真正的"工具"（`StringUtil` / `FileOperationUtil` / `AlgorithmUtil`）也在 `Utils/Util/` 里，和框架系统混在一起。
- 于是 `Core` 必须引用 `Utils`（`Core/ReunionMovement.Core.asmdef`），而 `GameEngine` 直接调模块：`Core/GameEngine.cs:707-741` 里直接读 `PauseSystem.Instance`。

### 7. 巨型类

| 文件 | 行数 | 内在职责 |
|---|---|---|
| `Core/System/UIInputSystem/UIInputSystem.cs` | 3279 | 13 个 region：初始化、Action 加载、重绑定、绑定持久化、焦点管理、UI/Gameplay 模式、UISystem 事件、设备轮询、导航派发、焦点域、玩家槽位、设备绑定 |
| `Core/System/UISystem/UISystem.cs` | 1264 | 窗口池、加载、层级、栈、静态 UI、超时、事件 |
| `Core/System/SoundSystem/SoundSystem.cs` | 1198 | 音乐交叉淡入、音效池、缓存、总线、并发去重 |
| `Core/GameEngine.cs` | 854 | 状态机、静态事件、模块增删、Update 桥接、应用状态、清理 |
| `Utils/Util/AlgorithmUtil.cs` | 1272 | 判断 / 计算 / 查找 / Engine / 集合，五件事 |
| `Utils/UI/ImageExtensions/Runtime/ImageEx.*.cs` | 977 + 871 + 554 | 属性、运行时、材质辅助混在一起 |

### 8. 示例、业务、框架三合一

- `Scenes/Example/` 里 20+ 示例场景和 `Scenes/Temp.unity`（业务启动场景）平级。
- `Utils/StateMachine/Example/`、`Utils/Download/Example/` … 每个系统自带 `Example/` 子目录，和运行时代码同级。
- `UI/Select/` 是"本地多人选人 + 设置面板"的业务界面（9 文件 / 2,998 行，占 `UI/` 全部），其中只有 `CarouselSelectionController` 是可复用组件，其余都是这个 demo 的界面逻辑。
- `Editor/UIExamples/CreateLocalMultiplayerSelectionExample.cs` 777 行，是**为某个 demo 生成资源的工具**，占 Editor 代码 16%。

> 代价：新人分不清"这是框架能力"还是"这是这个项目的业务"。

### 9. 护栏缺失

- 11 个测试文件，`ReunionMovement.Tests.asmdef` 仅 Editor 平台，没有 CI 配置。
- 没有 `.editorconfig`，没有分析器；类型后缀 `System` / `Mgr` / `Util` / `Manager` / `Helper` 并存。
- `README.md` 208 行是**特性清单**（营销向），没有"架构总览 / 启动时序 / 新增模块怎么做"。
- `Docs/` 里 9 篇文档都是**某个功能**的说明，缺入口级文档。

## 四、目标结构

```
Assets/ReunionMovement/
├── Framework/                      ← 框架本体（未来可整包提取为 UPM）
│   ├── Base/                       ← 零依赖：接口、枚举、结果类型、ModuleId
│   ├── Runtime/                    ← 引擎与基础设施
│   │   ├── Engine/                 ← GameEngine / GameEngineDriver / Bootstrap / ModuleCatalog
│   │   ├── Platform/               ← WebGL 桥接、平台判断、PlatformTimeout
│   │   └── Diagnostics/            ← Log / ErrorReporter / PerformanceMonitor
│   ├── Modules/                    ← 一个系统一个文件夹
│   │   ├── Resource/ Addressable/ Scene/ UI/ UIInput/ UIToolkit/
│   │   ├── Audio/ Localization/ Network/ Http/ Download/ Timer/
│   │   └── StateMachine/ ObjectPool/ Save/ Gacha/ Terminal/
│   ├── Editor/                     ← 框架自带编辑器工具
│   └── Tests/
├── Utilities/                      ← 纯工具：无状态、静态、可单测
├── Game/                           ← 宿主层：本项目的业务
│   ├── Entry/                      ← MyGameEntry / GameModules
│   ├── UI/                         ← StartGameUIPlane / SettingsPanel
│   └── Scenes/                     ← Boot / Temp
├── Samples/                        ← 示例（后期迁移为 UPM 的 Samples~，按需导入）
└── Resources/ Fonts/ Shaders/ Plugins/ 3rd/
```

**依赖方向（只能向下）**

```
        Game
         │
    Framework.Modules
         │
  Framework.Runtime ──► Utilities
         │
   Framework.Base
```

**五条铁律**（写成 Editor 测试，违反即红）：

1. `Base` 不引用任何 ReunionMovement 程序集。
2. `Runtime` 不引用 `Modules` —— 需要模块配合时，**发事件**，让模块自己订阅（现在的 `GameEngine` ↔ `PauseSystem` 就是反例）。
3. `Modules` 之间默认互不引用；确需依赖的（如 UI 依赖 Resource）显式声明 `DependsOn`，由 `ModuleCatalog` 校验。
4. `Game` 可以引用一切，反向永远不成立。
5. `Utilities` 不依赖引擎 / 不依赖 Runtime，纯函数，可单测。

> **不建议**一开始就拆 15 个模块级 asmdef。asmdef 越多，"新建文件"就越要先想"属于哪个程序集"，与"好上手"的目标相反。先用 4 个主程序集 + 文件夹隔离，等框架稳定、要对外发包时再按需拆分。

### 阶段 1 · 入口可插拔（1–2 人日，低风险）★ 收益最大

**1.1 让 GameEntry 可声明，而不是写死**

`Core/Bootstrap.cs`

```csharp
// 宿主在自己的程序集里声明一次，框架据此创建入口
[assembly: ReunionGameEntry(typeof(ReunionMovement.Game.MyGameEntry))]
```

```csharp
[AttributeUsage(AttributeTargets.Assembly, AllowMultiple = false)]
public sealed class ReunionGameEntryAttribute : Attribute
{
    public Type EntryType { get; }
    public ReunionGameEntryAttribute(Type entryType) { EntryType = entryType; }
}
```

`Bootstrap` 在 `SubsystemRegistration` 阶段反射读取；没有声明时退回内置的 `StartGame`（保持向后兼容）。同时提供手动入口：

```csharp
Bootstrap.Disable();                       // 关掉自动启动
await Bootstrap.StartAsync(new MyGameEntry());   // 自己掌控
```

**1.2 把"玄学"变成配置**

```csharp
public sealed class BootstrapOptions
{
    public bool AutoStart = true;
    public string[] TestScenePrefixes = { "Test", "_" };   // 前缀匹配，不再用 Contains
    public string[] TestSceneContains = { };               // 需要时显式配置
}
Bootstrap.Options = new BootstrapOptions { ... };
```

**1.3 `StartGame` 瘦身成"示例宿主"**

| 抽出去 | 去往 | 原因 |
|---|---|---|
| WebGL 全屏 P/Invoke + `OnBrowserFullscreenChanged` + `SetFullscreen` | `Framework/Platform/WebGL/WebGLFullscreenBridge.cs` | 平台代码，与"游戏入口"无关 |
| `"Temp"` / `"StartGameUIPlane"` | `Game/GameFlow.cs` | 业务场景流 |
| 14 个模块的注册 | `Game/Entry/GameModules.cs` | 宿主自己决定要哪些模块 |
| `ResetStatics` 的 7 个硬编码 | `Framework/Runtime/StaticResetRegistry.cs` | 改成 `IStaticResettable` 自动发现 |

**验收**：新建一个空工程，只写一个 `MyGameEntry` + 一行 assembly 特性，不改任何 `Framework/` 文件即可跑起来。这条验收就是"上手是否合格"的硬标准。

### 阶段 2 · 模块契约与统一访问（2–3 人日，中低风险）

**2.1 模块声明依赖，引擎校验**

```csharp
public abstract class GameModule : ICustomSystem, ISystemDisposable
{
    public virtual int Order => 0;                       // 同层内排序，小的先
    public virtual Type[] DependsOn => Array.Empty<Type>();
    public virtual UniTask Init() => UniTask.CompletedTask;
    public virtual void Clear() { }
}
```

`ModuleCatalog.Build(declared)`：拓扑排序 + 环检测 + 缺依赖报错 + 重复注册报错，**在启动前一次性报清楚**，而不是运行到一半资源为空。

`StartGame` 里的数字注释全部删除 —— 顺序由 `Order` / `DependsOn` 决定。

**2.2 统一访问方式**

```csharp
public static class Modules
{
    public static T Get<T>() where T : class, ICustomSystem;      // 未注册时抛出"明确告诉你少了什么"的异常
    public static bool TryGet<T>(out T module);
}
```

- `XxxSystem.Instance` 标 `[Obsolete("改用 Modules.Get<T>()")]`，保留 1–2 个版本给示例代码迁移。
- `MonoBehaviour SingletonMgr<T>` 的管理器（`TimerMgr` / `HttpMgr` / `NetworkMgr` / `DownloadMgr`）改为**纯 C# 模块**，由引擎托管；去掉 `private void Update()` 兜底和 `ModuleRuntime.IsEngineRunning`。
- 删掉 `Core/Base/ModuleRuntime.cs`。这是本次重构里最"解气"的一步：它存在只是因为分层错了。

**2.3 打断 `GameEngine` → `PauseSystem` 的直连**

`Core/GameEngine.cs:707-741` 现在直接读写 `PauseSystem.Instance`。改成：`GameEngine` 只发 `OnAppPauseSubject`（已有），`PauseSystem` 自己订阅并决策。Runtime 层从此不再认识任何具体模块。

**验收**：`Framework.Runtime` 的 asmdef 里删掉对 `Modules` 的引用后仍能编译；启动日志能打印"模块依赖排序结果"。

### 阶段 3 · 分层与命名归位（3–5 人日，中风险）

这是唯一"动路径"的阶段，风险集中在这里，必须按下面顺序做：

1. **先动程序集，不动命名空间** —— 先把 `Utils` 拆成 `Framework.Modules` + `Utilities`，`Core` 改成 `Framework.Runtime`，中间保留一个版本的类型转发（`[assembly: TypeForwardedTo]` 或用 `global using` 别名）以免示例全红。
2. **再动命名空间** —— `ReunionMovement.Common.Util.*` → `ReunionMovement.Framework.Modules.*`，用 IDE 批量重命名，**不要手改字符串**。
3. **最后动目录** —— 在 Unity 编辑器里拖动文件夹（保留 `.meta` 和 GUID），或 `git mv 文件 + .meta` 一起移动。**绝不要**只移 `.cs` 不移 `.meta`，否则所有 prefab / scene 引用断裂。

> 命名空间改名会波及 `Addressables` 的地址（部分地址是 `类型全名` 生成的）。做完之后跑一次「Addressables → 校验地址」，把断掉的 key 补齐。

## 九、不要做的事

1. **不要动 R3 / UniTask / DOTween。** 它们是这个项目性能与异步的地基，换掉是纯负收益。
2. **不要重写网络栈。** 四传输 + 编解码 + 心跳 + 重连 + RPC 已经能用，只在阶段 2 里换个"谁驱动它"。
3. **不要一次性改命名空间。** 先程序集、再命名空间、最后目录；每步单独 PR。
4. **不要为了"简单"把所有系统改成 MonoBehaviour。** 方向正好相反。
5. **不要立刻引入 DI 容器（VContainer 等）。** 等 `Modules.Get<T>()` 稳定后再说 —— 那时接口已就位，替换成本很低；现在引入只会让新人多学一套概念。
6. **不要拆 `LoopScrollRect`、`ImageEx` 的着色器逻辑。** 收益低、回归风险高。
7. **不要把框架塞进 UPM 包。** 至少在阶段 0–3 完成前不要 —— 包内改文件会触发重新导入，迭代速度直接砍半。

## 十、Unity 特有的坑（执行时逐条对照）

1. **移动文件必须连 `.meta` 一起。** 用编辑器拖动，或 `git mv a.cs a.cs.meta`。否则 prefab / scene 里的脚本引用变 `Missing`。
2. **改 asmdef 引用优先用 GUID。** `"GUID:xxxx"` 形式，避免重命名后引用失效。
3. **关闭 Domain Reload 的兼容要保住。** 阶段 1 的 `StaticResetRegistry` 就是为此，别删。
4. **Addressables 的地址可能含类型全名。** 阶段 3 改命名空间后要重新校验地址表。
5. **WebGL 没有 `System.Threading.Timer`。** 现有 `PlatformTimeout`（PlayerLoop 驱动）必须保留，新的超时逻辑不要用 `Task.Delay` / `CancellationTokenSource(TimeSpan)`。
6. **示例场景靠场景名触发"跳过跳转"。** 阶段 1 改成前缀配置后，要同步改所有 `*Example.unity` 的名字，否则示例会开始自动跳场景。
7. **`Temp.unity` 是业务启动场景，不是框架资源。** 阶段 1 移到 `Game/Scenes/` 时同步改 Build Settings 顺序。
